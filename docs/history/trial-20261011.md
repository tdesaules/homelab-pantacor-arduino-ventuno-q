## Correction de la surveillance

L'essai précédent lançait un garde enfant qui attendait que Pantavisor monte
`/proc`. Le garde pouvait quitter avant d'avoir assuré le retour. Ce défaut de
conception a été corrigé ; il ne prouve pas à lui seul la cause de l'ancien échec.

Le nouveau `/init` est un **exécutable ARM64 statique**, sans interpréteur ELF
ni dépendance au shell ou aux bibliothèques partagées pour son démarrage. Il :

1. reste **PID 1**, avec le nom `ventuno-init` ;
2. arme une alarme de secours avant les montages ;
3. monte lui-même proc, sysfs, devtmpfs, devpts et un `/run` volatile ;
4. charge et tente d'armer le watchdog matériel ;
5. lance une collecte indépendante qui vérifie le marqueur de l'essai et écrit
   un premier jalon sur l'eMMC en C, avant tout lancement de Pantavisor ;
6. lance Pantavisor **comme enfant en mode standalone**, seulement après ce jalon ;
7. demande un reboot après 180 secondes, avec une alarme de secours à 190 secondes.

Le watchdog matériel a effectivement été observé **actif, délai 30 secondes**
pendant l'essai. Son expiration n'a pas été provoquée séparément : le test valide
le retour automatique de l'ensemble, pas chaque mécanisme de reset isolément.

**Ce n'est pas encore Pantavisor comme PID 1, ni le mode embedded avec révisions
et conteneurs.** Le changement volontaire de rôle permet de diagnostiquer le
runtime sous une surveillance indépendante.

## Problème Wi-Fi identifié et correction préparée

Le noyau identifie la radio comme **QCA2066 hw2.1**, puis échoue sur :

```text
Direct firmware load for ath11k/QCA2066/hw2.1/amss.bin failed with error -2
```

Les déclarations génériques `modinfo` mentionnaient notamment WCN6855 mais
n'étaient pas suffisantes pour déduire tous les chemins de ce BSP. La capture
constructeur contient bien les fichiers QCA2066 ; ils avaient été exclus par
notre réduction.

La politique inclut désormais explicitement les fichiers `amss.bin`,
`board-2.bin`, `m3.bin` et les fichiers associés de QCA2066. Une image corrigée a
été assemblée et vérifiée dans **`artifacts/prototype-1084-supervised-qca2066/`** :

- 112 modules et 56 fichiers de firmware ;
- initramfs de **35 640 986 octets**, environ 34,0 Mio ;
- SHA-256 : `005112c560fd43b5b482cb820a8c28e62fa32c05a5d7c2ead98fe61d947955de`.

**Cette correction n'a pas encore été testée sur le matériel.** L'image ayant
réussi l'aller-retour mesuré ci-dessus est conservée séparément :

- `artifacts/prototype-1084-supervised/`, 30 801 880 octets ;
- SHA-256 : `c52c9908a007a008aeb8a88ce3e0611f7d471c220ba7b6e59e92f243b1dd1756`.

## Reproduire et poursuivre

```bash
bash scripts/build-initramfs.sh
python3 scripts/assemble-prototype.py \
  artifacts/build/tmp/deploy/images/ventuno-q/pantavisor-initramfs-ventuno-q.cpio.gz \
  --trial --output-dir artifacts/prototype-1084-supervised-qca2066
python3 scripts/verify-prototype.py --output-dir artifacts/prototype-1084-supervised-qca2066 --emulate
python3 scripts/test-supervised-boot.py --output-dir artifacts/prototype-1084-supervised-qca2066
```

`transfer-trial.py` prépare un nouvel identifiant et vérifie le système cible.
Les étapes `install-trial.sh`, `start-bounded-trial.sh` et `finish-trial.sh`
acceptent cet identifiant via `run-board-check.py --argument ID`. La phase
`start` redémarre réellement la carte ; la phase `finish` restaure GRUB après
contrôle des empreintes. Ne pas rejouer les commandes de démarrage de l'essai
déjà terminé.

Prochaines validations : firmware Wi-Fi corrigé sur matériel, identité réseau
et IPv4/SSH, puis passage progressif au runtime Pantavisor/PID 1 et au stockage
des révisions. Aucun nouveau boot custom n'a été lancé après ce résultat.
